## The export failed once, on a locked leftover keychain

Worth recording in full, because it is a new failure mode and it will come back. The first `-exportArchive`
(18:47:11 → 18:47:31) ended:

```
error: exportArchive codesign command failed (… /Payload/Inborn.app/Frameworks/ExpoModulesJSI.framework:
  replacing existing signature
… ExpoModulesJSI.framework: errSecInternalComponent
)
** EXPORT FAILED **
```

`errSecInternalComponent` from `codesign` means the private key could not be used, and the cause was on the Mac, not in
the archive. The distribution identity this export re-signs with lives **only** in Xcode's temporary
`~/Library/Keychains/signing_temp.keychain-db`:

| keychain | `iPhone Distribution: Moshe Cohen (NGCHN95667)` | `Apple Development: Moshe Cohen (WUCEF6CXDH)` | state |
|---|---|---|---|
| `login.keychain-db` | no | yes | unlocked, `no-timeout` |
| `signing_temp.keychain-db` | **yes** | no | **locked** — `show-keychain-info` answers "Unable to obtain authorization" |

A stale `signing_temp` (mtime 18:22, left by an earlier run that did not finish its pipeline) was sitting **first** in
the user's keychain search list, so `codesign` picked the distribution identity out of a keychain it could not unlock.
The login keychain was never locked and no password prompt was involved — which matters, because a password dialog on
Moshe's screen is exactly what these runs must never raise.

The fix, and it needs no password: drop the dead keychain from the search list and let Xcode make its own.

```
security list-keychains                                   # record the original list first
security list-keychains -s ~/Library/Keychains/login.keychain-db /Library/Keychains/System.keychain
```

The identical export command then succeeded on the first try, 18:49:29 → 18:50:09. **Xcode created a fresh temporary
keychain, fetched the cloud-managed distribution certificate into it, signed, and deleted the file afterwards** — after
the run `signing_temp.keychain-db` no longer exists, so the search list was left at `login` + `System`, which is the
correct default and not something to restore. A copy of the stale file was taken before the change and kept in the
session scratch dir; nothing in the login keychain was touched, read or altered.

If `errSecInternalComponent` shows up again, check `security list-keychains` and
`security show-keychain-info <each one>` before anything else. Do **not** reach for `security unlock-keychain`: an
empty password is refused, and the real password is not ours to supply.

## The upload failed once too, on a key another stream deleted

`altool --validate-app` returned `VERIFY SUCCEEDED with no errors` at 18:51:12. The `--upload-app` that ran **one
second later** failed instantly:

```
ERROR: Failed to load AuthKey file. (-43) The file AuthKey_REDACTED-ASC-KEY.p8 could not be found in any of these
locations: … '~/.appstoreconnect/private_keys'.
```

The key had been staged for the export and was still there for the validate. `scripts/asc-key-env.sh --cleanup` deletes
**every** `AuthKey_*.p8` in that directory, not only the one its own caller staged, so any concurrent stream finishing
its own iOS work in that 61-second window takes this run's key with it. Nothing was wrong with the key or the archive:
re-staging it and repeating only the upload succeeded.

The durable lesson for the next stream: **stage the key immediately before each altool call, not once for the whole
pipeline** (`scratchpad/ios-build-13/upload-only.sh` does exactly that). Making `--cleanup` delete only the caller's
own file would be the real fix and is not this stream's to make.

`--upload-app` → `UPLOAD SUCCEEDED with no errors` (18:53:26), 561,058,431 bytes in **12.537 seconds**
(44.8 MB/s, 358 Mbps), delivery UUID `b11ec89b-39bb-4c06-87b7-430f71bb6676`.
