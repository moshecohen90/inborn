# Fixes round 21 — the web build crashed on the first onboarding click (F40), the desktop shell wore the browser's door (F41)

Branch `web-desktop-check`, 22.9.2026, from `main` 6899f07. Both findings came off the **real web build** and the
real desktop `.app` on 22.9, not off a test.

## F40 — Continue on the web onboarding killed the page

Opening `http://127.0.0.1:8477`, taking the download door, then pressing **Continue** on S01 left a blank page. The
console line was

```
pageerror: Cannot read properties of undefined (reading 'get')
```

**Root cause.** S02 (`screens/Onboarding/ModelChoice.tsx`) reads `useInstalledModel` from `../../vault`, and
`vault/index.ts` re-exports `resolveEngine` from `vault/resolve.ts`, which imports `adapters/llamaRn.ts`, which
imports `llama.rn`. `llama.rn` calls `TurboModuleRegistry.get("RNLlama")` at module scope. react-native-web has no
`TurboModuleRegistry`, so the property read threw the moment Metro evaluated that module — which is when the router
pulled S02 in, one click into onboarding. The import was harmless on the phones and invisible to every test, because
nothing on the web had ever opened that screen.

**Fix.** `apps/mobile/src/vault/resolve.web.ts` — a Metro platform variant whose `resolveEngine()` returns `null`.
The browser and the Tauri shell pick their engine in `adapters/devModel.web.ts` (wllama / OPFS) and
`adapters/tauri.ts` (the Rust vault) respectively, so the vault's native resolver has nothing to say there, and with
the `.web.ts` file in place `llama.rn` never enters the web bundle at all. This is the same discipline
`screens/vault/VaultEntry.web.tsx` and `vault/tiers.ts` already use.

A second web-only trap on the same path: `VaultStore.modelLocation()` called `devFallbackFile()`, which builds an
`expo-file-system` `File` under the document directory — a directory no browser has. `vault/store.ts` now skips the
dev fallback unless `Platform.OS !== "web"`.

## F41 — the desktop shell was wrapped in the browser's download door

`WebShell` is mounted from `app/_layout.tsx` for every web-platform build, and the Tauri shell **is** a web-platform
build. So the desktop window got the browser's notice strip ("Runs locally in your browser… Get the app") and, worse,
the download door — a gate asking the user to download a model the Rust vault already holds. The doors read
`web/boot.ts`, which the desktop never runs: `adapters/prepare.web.ts` sends the shell to `prepareTauri()` instead.

**Fix.** `apps/mobile/src/web/doors.ts` — `webDoorsApply()`, one predicate over the existing `isTauri()`. `WebShell`
renders `BrowserShell` only when it is true and passes its children straight through otherwise, so the desktop window
shows the app and nothing else.

## The gate hole, and closing it

`pn web:smoke` covered the download door, OPFS, the offline visit, the phone door and the no-space door — and it
**passed on the broken build**. Its context set `localStorage["inborn.prefs"] = {onboarded:true}` in an init script,
so the smoke had never once opened an onboarding screen. F40 lived on a code path the gate stepped over.

`scripts/web-smoke.mjs` now walks the real thing on the first visit: download door → **S01 Welcome → S02 model →
S03 airplane → S04 sealed → S05 lock** → chat → one prompt, checking for a page error after every screen and after
every click, so a dead page fails in seconds instead of timing out. The old `skipOnboarding` init script stays only on
the two contexts that never get past the door (phone, no-space).

**Negative control, run today.** With `vault/resolve.web.ts` moved aside, `pn web:build` rebuilt and `pn web:smoke`
re-run, the smoke exits 1 at exactly the right step:

```
FAIL: onboarding-welcome (after the click): the page threw Cannot read properties of undefined (reading 'get')
```

Screenshot of that failure: `docs/qa/fixes-r21/fixes-r21-00-f40-crash-before.png`. The file was then restored and
everything below was run against the fixed build.

A second tripwire runs without a browser. `apps/mobile/test/webBundle.test.ts` walks every route under `src/app`
using Metro's web resolution order (`.web.*` wins) and fails if a module with no react-native-web implementation is
reachable — `llama.rn`, `whisper.rn`, `expo-iap`, `expo-sqlite`, `expo-speech-recognition`,
`@fugood/react-native-audio-pcm-stream`. It reports the import chain when it fires, and it fails on the unfixed tree:

```
app/onboarding/model.tsx -> screens/Onboarding/ModelChoice.tsx -> vault/index.ts -> vault/resolve.ts
  -> adapters/llamaRn.ts -> llama.rn
```

`apps/mobile/src/web/doors.test.ts` pins F41's gate in three cases: a plain browser gets the doors, a window carrying
`__TAURI__` does not, and a runtime with no `window` counts as a browser.

## The Keychain prompt on rebuilt desktop builds

Not a QA finding — the reason the desktop app annoyed Moshe. The chat database is SQLCipher and its key is a
login-Keychain item (`com.inbornapp.desktop` / `chat-db-key`, `apps/desktop/src-tauri/src/store.rs`). A Keychain
item's ACL names the application that created it; an **ad-hoc** signature (`"signingIdentity": "-"` in
`tauri.conf.json`) identifies an app only by its own code hash, so every rebuilt `Inborn.app` is a stranger to the
item and macOS asks for the login password at launch.

`corepack pnpm desktop:build:app` and `desktop:build` now run through
`apps/desktop/scripts/with-signing-identity.sh`, which exports `APPLE_SIGNING_IDENTITY` from the first **Apple
Development** identity in `security find-identity -v -p codesigning` (on this Mac: `Apple Development: Moshe Cohen
(WUCEF6CXDH)`). That certificate's designated requirement is identifier + team and does not change between builds, so
one "Always Allow" holds for every rebuild after it. `APPLE_SIGNING_IDENTITY` set by hand still wins; with no identity
on the machine the ad-hoc signature applies exactly as before. Release builds already used Developer ID and never
prompted. The QA recipe for an item created by an older ad-hoc build, with the real service and account names, is in
`apps/desktop/README.md` under "QA launches without keychain prompts".
