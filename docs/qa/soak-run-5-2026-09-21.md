# Soak run 5 — versionCode 9 on the OnePlus 6T, after a real Play update from vc8, 21.9.2026

**PASS.** Twenty-six F33 pop cycles, twenty-six OK, one app process for 2 h 31 min, zero Inborn crashes, and the
phone's own crash store is byte-identical before and after the run — no entry for versionCode 8 or 9 at all. The
build under test reached the phone the way a tester's would: Google Play updated vc8 to vc9 in place, with no
uninstall.

Soak run 4 proved the round-14 F33 fix on vc8 (`docs/qa/soak-run-4-2026-09-21.md`). This run repeats it on vc9,
which adds fixes rounds 15 and 16, and it carries the three round-15 retests that vc8 failed or could not answer.

## Build under test

versionCode 9, versionName 1.0.0; About reads **1.0.0 (9)** and commit **f27a8c59b3b6** (= `main` f27a8c5).
Delivered by Google Play to the internal track and installed by `com.android.vending` at **12:24:02** as an

## Method

`adb -s <6t-serial>`, keys only (TAB / DPAD / ENTER / `input text`), every `uiautomator dump` serialised behind one
lock, and **one driver process** — soak 4's 22 `uiautomator` FATAL lines came from a second sender sharing the
accessibility connection, so this run never starts one. Driver in the session scratch under `soak5/`, built from
the soak-4 driver with two changes: a cycle counts `FATAL EXCEPTION` from an **app-scoped** capture
(`adb logcat --pid=28601`) rather than the full log, so a harness crash cannot produce a false CRASH verdict, and
the sampler runs every 5 minutes instead of 10.

Three captures ran for the whole window: `logcat -v time` (full, 2,547,809 lines), `logcat -v time --pid=28601`
(the app alone, 74,481 lines) and `logcat -b events -v time`. `dumpsys dropbox --print` was taken before the run
and again after it.

The **F33 sequence**, once per cycle, is the one round 14 names as the repro: HOME → 60 s → launcher relaunch →
10 s → `am start -a android.intent.action.VIEW -d inborn://vault` with a chat of ≥ 6 messages in the foreground →
3 s → BACK, which pops `/vault` and re-attaches the chat's whole view tree. Each cycle records the app pid before
and after and the delta in `FATAL EXCEPTION` and in `am_proc_died` for the package. A cycle is CRASH if the pid
changed or either delta is non-zero.

Around the cycles the driver ran the soak-3 prompt rotation over Instant and Fast, sampled `meminfo`,
`thermalservice` and `battery` every 5 minutes, read the ledger and opened a new chat every 20 minutes, switched
model every 25 minutes and visited vault, settings, proof and chats.

**Run window.** Cycles 1–18 are the 120-minute run, 12:39:58 → 14:40:46. Cycles 19–26 were run back to back
immediately afterwards, 14:41:31 → 14:55:40, to clear the 24-cycle floor the brief asks for; they use the identical
sequence, only without the idle gap between them. The app process did not restart at any point, so all 26 cycles
are one continuous session. Why the timed run produced 18 rather than 24 is in "Honest notes".

## F27 — fixed on the floor device

Section K reproduced the TAB focus trap on **vc8 on this phone**: sixteen consecutive stops inside the suggestion
chips, never reaching the composer. On vc9 it is gone. Eighteen TABs on a fresh empty chat give two identical
nine-stop rings and reach `composer-input` at tab 9 and again at tab 18:

```
tab 1 -> [open-chats]        tab 10 -> [open-chats]
tab 2 -> [model-chip]        tab 11 -> [model-chip]
tab 3 -> [attach]            tab 12 -> [attach]
tab 4 -> [mic]               tab 13 -> [mic]
tab 5 -> [] (notice Dismiss) tab 14 -> [] (notice Dismiss)
tab 6 -> [suggestion-summarize] tab 15 -> [suggestion-summarize]
tab 7 -> [suggestion-translate] tab 16 -> [suggestion-translate]
tab 8 -> [suggestion-draft]  tab 17 -> [suggestion-draft]
tab 9 -> [composer-input]    tab 18 -> [composer-input]
```

Six non-chip stops follow the first chip, where vc8 had zero. This is exactly the ring round 15 measured on a debug
APK of `fixes-r15`, now confirmed on the Play-signed release build that a tester receives. A hardware-keyboard or
switch-access user can reach the composer from an empty chat. Evidence: `soak5/run5/f27-ring.txt`,
`f27-empty-chat.xml`, `f27-empty-chat.png`.

## Fast after the Play update — the vault no longer asks for 1.2 GB it already has

This is round 15 finding C on the real update path, and **nothing was tapped** to make it pass.

On vc8, section K recorded the vault reading "508 MB in the vault" straight after the update, with the Fast card
offering `install-fast` "Install · 1.2 GB from Google Play" — a download that then completed instantly because the
bytes had never left the phone. On vc9, at the same point in the same sequence, the vault reads
**"1.7 GB in the vault · 14 GB free"**, Fast reads **Loaded · In use**, and the dump of the screen contains **no
`install-fast` node and no "Install" text at all**.

The log says who did it. Opening the vault fired `AssetPackServiceImpl : onRequestDownloadInfo()` at **12:26:01**;
**two seconds later**, at 12:26:03, `[inborn] engine model fast from
file:///data/data/com.inbornapp.mobile/files/assetpacks/inborn_model_fast/9/9/assets/Qwen3.5-2B-Q4_K_M.gguf` — the
versionCode-9 path, reached with no download. A 1.2 GB fetch cannot happen in two seconds. `requestKnownPacks`
re-bound bytes that were already on the device, which is what the fix claims. Fast then answered "Name three
colours." in 15 s with the chip reading FAST. Evidence: `soak5/run5/21-vc9-vault.png`, `vault-vc9.xml`,
`logcat-update.txt`, `24-vc9-fast-answer.png`.

## Honest notes on the run

1. **The timed run made 18 cycles, not 24, and the driver is why.** The loop keeps the F33 events on a 5-minute
   wall-clock grid and only starts a prompt when there is room for it before the next cycle is due, but the
   per-prompt cap (45 dump iterations, about 110 s) is longer than the 70 s of room the gate requires, so a long
   answer on the 2B model regularly pushed a cycle past its slot. Cycles landed 5 to 9 minutes apart instead of 5.
   The next soak should set the cap below the gate. The eight back-to-back cycles afterwards close the gap; they
   ran on the same process against the same build, so they measure the same thing.
2. **13 of 45 turns timed out, none failed.** "Timed out" means the driver stopped watching, not that the app
   stopped answering: `stop-seen=1` on every one of them, so the model was still streaming when the cap expired.
   The three depth fillers before cycle 1 cost 84 s, 83 s and 7 s for "What is 2 plus 2?" on the 2B model for the
   same reason.
3. **One `SEND-FAIL` is in the events log, at 12:33:27, before the run started.** It came from the sanity pass:
   BACK out of the About screen lands on the vault, not on the chat, so `to_composer` had no composer to focus.
   Pressing `close-vault` recovers. Inside the run window there were zero send failures.
4. **Keeping to one driver process worked.** Soak 4's 22 `uiautomator` FATALs do not recur: this capture has zero
   FATAL lines of any origin.
