# Soak run 7 — versionCode 14 on the OnePlus 6T, updated in place from vc13 — 22.9.2026 03:44–04:44

Soak 6 ran vc13 for an hour and ended with the finding that became **F38**: the same three-word arithmetic question
answered in 8 s the first time it was asked in a chat and ran to the driver's ceiling on every repeat. Round 19 landed
the answer-length policy (`packages/core/src/chat/length.ts`); this run is the same hour on **vc14**, the first build
that carries it, delivered by Google Play as an **update in place** over vc13 with every asset pack on the phone.

**It also corrects soak 6.** The 83–87 s figures in soak 6 were the measuring driver running out its poll ceiling, not
the model. See "What this run changes in the driver" below; the same repeated question completes here in 8–17 s.

## Method

`adb -s <6t-serial>`, keys only (TAB / DPAD / ENTER / `input text`), every `uiautomator dump` serialised behind one lock
directory, and **one driver process** — soak 4's lesson. Driver in the session scratch under `android-vc14/drv/`, soak
6's cadence unchanged: F33 every 5 minutes, a `meminfo` / `thermalservice` / `battery` sample every 5, a new chat every
18, a model switch every 15, a deep-link visit to vault, settings and proof every 15, prompt cap 45 polls.

Two captures ran for the whole window: `logcat -v time --pid=<app>` and `logcat -b events -v time`. `dumpsys dropbox`
was read before the run and again after it.

## What this run changes in the driver, and why the counts are not comparable with soak 6

Soak 6's sender called a turn complete when the last assistant line differed from its value before the send and then
held still. It read that line from `assistant-message`'s `content-desc`, which carries only the answer's first
paragraph. Two identical answers to the same question have the same first line, so on a repeat the test could never
fire: the turn ran to the poll ceiling and was recorded as a timeout at 83–87 s. That is the whole of soak 6's timeout
count, and the round-19 note that reads those numbers as a model problem is wrong.

The sender used here calls a turn complete when the **stop button** has been seen and is then absent twice, with a
fallback for answers short enough that no dump catches the button: the full answer text, read from every TextView under
the message, holding still for three dumps. **Soak 7's timeout count is therefore not comparable with soak 6's** — the
old count measured the detector. Everything else in the loop is unchanged.

## One process restart, and it was the run's own doing

Between the proofs and the soak the app's pid changed from 18707 to 15910. It was not a crash. The events log names the
cause:

```
09-22 03:40:52.322 I/am_kill     ( 1943): [0,18707,com.inbornapp.mobile,0,permissions revoked]
09-22 03:40:52.443 I/am_proc_start( 1943): [0,15910,11436,com.inbornapp.mobile,qcomUXE,]
```

That is `pm revoke android.permission.RECORD_AUDIO`, which the F35 proof runs to put the microphone back the way it
found it. Android kills an app when a runtime permission is revoked under it. `am_kill` with reason
`permissions revoked`, no `am_crash`, no `am_anr`, and no new dropbox entry.
