# Soak run 4 — versionCode 8 on the OnePlus 6T, 21.9.2026

**PASS. F33 is gone.** Forty-eight pop cycles of the exact sequence that killed vc7, zero crashes, one process
throughout, and the phone's own crash store holds no vc8 entry at all.

Soak run 3 killed vc7 on this phone with `java.lang.NullPointerException … View.getVisibility()` at
`ViewGroup.dispatchAttachedToWindow` under `ScreenStack.onUpdate`, 153 ms after the BACK that popped `/vault`
(`docs/qa/soak-run-3-2026-09-20.md`). Fixes round 14 disabled `removeClippedSubviews` on the four lists that can
be mounted when a screen is popped back to, and the crash never reproduced on an emulator, so this run on the
floor device is the only real evidence the fix works.

## Method

`adb -s <6t-serial>`, keys only (TAB / DPAD / ENTER / `input text`), uiautomator dumps serialised behind one lock.
Driver in the session scratch under `soak4/`, built from the soak-3 driver.

The **F33 sequence**, once per cycle, is the one round 14 names as the repro: HOME → 60 s → launcher relaunch →
10 s → `am start -a android.intent.action.VIEW -d inborn://vault` with a chat of ≥ 6 messages in the foreground →
3 s → BACK, which pops `/vault` and re-attaches the chat's whole view tree. Each cycle records the app pid before
and after, and the delta in `FATAL EXCEPTION` lines and in `am_proc_died` for the package. A cycle is CRASH if
the pid changed or either delta is non-zero.

Around the cycles the driver ran the soak-3 prompt rotation over Instant and Fast, sampled `meminfo`,
`thermalservice` and `battery` every 10 minutes, read the ledger and opened a new chat every 25 minutes, and
visited vault, settings, proof and chats.

**Run window.** Cycles 1–24 are the 150-minute run, 04:36:36 → 07:06:36. Cycles 25–30 were run back to back
immediately afterwards, 07:11 → 07:24, to reach the 28-cycle floor the brief asks for; they use the identical
sequence, only without the idle gap between them. The app process did not restart at any point, so all 30 cycles
are one continuous session. Four earlier attempts that evening were stopped and restarted for driver faults, not
app faults — the app process survived every one of them too (see "Honest notes").

### The 22 FATAL lines in the capture are the harness, not the app

`grep -c "FATAL EXCEPTION"` over the capture returns 22, and none of them is Inborn. Every one is
`java.lang.IllegalStateException: UiAutomationService … already registered!` thrown by `uiautomator dump`
itself, all inside 05:01:40 → 05:09:09, the window in which a second driver process was briefly run alongside the
first and the two collided on the accessibility connection. The second driver was stopped, and the app was
unaffected: pid 17660 is unchanged across that window and cycles 4, 5 and 6 straddle it with verdict OK. The one
`am_proc_died` in the events buffer is pid **17653** at **00:56:58**, the vc7 process, from before vc8 existed.

This is why every cycle scopes its counters to the package and to the pid rather than trusting a global crash
count, and why the analysis below separates the two.

## Honest notes on the run

The 150-minute window was restarted four times between 02:05 and 04:36. Every restart was a fault in my driver,
never in the app, and the app process was never killed by any of them, so the crash-free window is in fact
continuous from 01:47. The faults, recorded because the next soak should not repeat them:

1. **A runaway generation can eat the schedule.** "Answer in Hebrew: what is the meaning of the word shalom" ran
   473 s on the 2B model, which is "No · Hebrew" in the catalog. The per-prompt wait is now capped.
2. **A helper called in a command substitution cannot update counters.** `R=$(send …)` ran in a subshell, so the
   turn counter never advanced and the depth-filler loop spun. Fixed, and the loop is now bounded.
3. **`logcat -b events -d` is not free.** Dumping the whole events buffer over adb cost about 40 s a call, four
   calls a cycle, which starved the prompt load. The counters now read from the capture files on the Mac.
4. **`grep -c … || echo 0` prints two values** when grep finds nothing, because `grep -c` prints `0` and still
   exits 1. That broke the delta arithmetic for two cycles of an earlier attempt.
5. **Two drivers must not share one accessibility connection.** Running a second sender alongside the loop
   produced the 22 `uiautomator` crashes above.

Attempt logs are kept alongside the final ones: `loop-start1.log` … `loop-start5.log`, `f33-start*.csv`.
