## F27 — TAB focus ring is trapped by the empty-chat suggestion chips

**Severity: high for hardware-keyboard and switch-access users; it is also what ended this soak.**

On the empty-chat screen, once keyboard focus reaches the three suggestion chips it never leaves them. TAB cycles `suggestion-translate → suggestion-draft → suggestion-translate → …` forever. The composer, send, attach, mic, the chats button and the model chip all become unreachable by TAB.

Verified live on a fresh empty chat with **no banner on screen**, so the chips alone cause it:

```
tab 1 -> [mic]        tab 6  -> [suggestion-translate]
tab 2 -> []           tab 7  -> [suggestion-draft]
tab 3 -> [suggestion-summarize]   tab 8  -> [suggestion-translate]
tab 4 -> [suggestion-translate]   tab 9  -> [suggestion-draft]
tab 5 -> [suggestion-draft]       tab 10 -> [suggestion-translate]
```

The composer is present and reachable in principle. From `dump-empty-chat.xml`:

```
composer-input   focusable=true  focused=false clickable=true  enabled=true
send             focusable=true  focused=false clickable=true  enabled=false
```

So this is a traversal-order defect, not a missing or disabled node (`send` is correctly disabled only because the composer is empty). Arrow keys escape it: DPAD_DOWN reaches `mic` and DPAD_LEFT from `mic` reaches `composer-input`. TAB behaves normally on a chat that already has messages (`open-chats → model-chip → attach → composer-input → mic → … → ledger-toggle`). After the trap was escaped with DPAD, a prompt sent and answered normally on the same process, so nothing was wedged.

## F28 — stale "paused in background" banner on a fresh chat

From at least 14:11 to 15:32 the empty chat carried "Paused while Inborn was in the background. The partial answer is kept. · CONTINUE" (`min61.png`, `min142.png`), on a chat that had never generated anything and so had no partial answer to keep.

The banner is **global app state, not per chat**: `Banners.tsx` renders it from `device.recommendation`, which `device/mapState.ts` sets to `{ kind: "paused" }` whenever the guard status is `paused`, with nothing in that path scoped to a conversation. It clears only when the guard leaves the `paused` status, which in practice means the user presses CONTINUE (`continueGeneration()`) or generation resumes, so opening a new chat does not clear it. Observed live: the banner disappeared as soon as a prompt was sent and answered.

No fix proposed here.

## Instrument errors in this run

1. **Background-banner detection was void.** The driver grepped run 1's wording, "Continue after interruption", but the shipping string is "Paused while Inborn was in the background". All five `banner=0` readings in `events.log` mean only that the old string was absent. The banner was in fact present on screen for much of the second half (F28).
2. **Driver lesson.** Reaching a control by pressing TAB until the focused resource-id matches is not safe: it assumes every focusable node is in one traversal cycle, which F27 breaks. A driver should locate the composer by resource-id and reach it with DPAD (`DPAD_DOWN` to `mic`, then `DPAD_LEFT`), bound the attempt, and re-check for a banner row before counting a send as failed.
3. The PID extraction in `analyze.sh` captured stray text, so its package-scoped grep printed nothing; the count was re-run directly and is 0.
