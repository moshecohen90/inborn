## F27 retest — the TAB trap still reproduces on vc7

**Result: FAIL. F27 is open.** The fixes-r12 commit message (`0b8f950`) states "F27, the TAB trap between the empty-chat chips, does not reproduce on Android 11 or 13". On this phone, on this build, it does.

Retest 1, on the empty chat of a cold launch (`72-f27-retest.png`, dump `dump-empty-chat-vc7.xml`, no banner on screen):

```
tab  1 -> [open-chats]          tab  9 -> [suggestion-draft]
tab  2 -> [model-chip]          tab 10 -> [suggestion-translate]
tab  3 -> [attach]              tab 11 -> [suggestion-draft]
tab  4 -> [composer-input]      tab 12 -> [suggestion-translate]
tab  5 -> [mic]                 …
tab  6 -> []                    tab 24 -> [suggestion-translate]
tab  7 -> [suggestion-summarize]

```

Retest 2, on a fresh empty chat opened from the chats panel — run 2's exact scenario (`81-f27-newchat-trap.png`, dump `dump-empty-chat-newchat.xml`, no banner, chips present):

```
start -> [composer-input]
tab 1 -> [mic]   tab 2 -> []   tab 3 -> [suggestion-summarize]
tab 4 -> [suggestion-translate]   tab 5 -> [suggestion-draft]
tab 6..12 -> translate / draft / translate / draft / translate / draft / translate
```

Once focus enters the chip group, TAB never leaves it: `suggestion-translate → suggestion-draft → …` forever, and `composer-input`, `send`, `attach`, `mic`, `open-chats` and `model-chip` are all unreachable by TAB. This is the same traversal-order defect run 2 described, on the same two chips, and it is what made `attach` unreachable when this run tried to open the attach sheet by keyboard.

One detail run 2 did not record, and the likely reason a retest can look clean: **on a first launch the ring passes through `composer-input` before it reaches the chips** (tabs 1–5 above). A tester who presses TAB a few times from a freshly launched app lands on the composer and sees nothing wrong. The trap closes only after focus has entered the chip group, which is what happens as soon as anyone tabs past the composer, or opens a new chat from the chats panel and tabs at all.

DPAD escapes it every time, in 17 s of driving: `DPAD_DOWN` reaches `mic`, `DPAD_LEFT` reaches `composer-input`. That escape is what run 3's driver uses, and it is why this run has continuous prompt load where run 2 stalled at minute 51.

## Document asks — not exercised, and why there is no route on this phone

Same verdict as run 2, with the reason pinned down further. Import needs the system file picker, and the picker needs a tap.

- **Injected taps do not reach the app.** A tap at the exact bounds of the `attach` node (`[48,1311][172,1435]`, centre 110,1373) changed nothing on screen. The same `input tap` injection, in the same session, pressed **Update** in the Play Store's native app page and started the vc7 download, so the injection works on this phone and it is the app's React Native surface that ignores it.
- **The keyboard cannot reach `attach` from an empty chat either**, because F27 traps the ring in the chips first: pressing TAB toward `attach` ended on `suggestion-translate`, and the ENTER that followed activated the Translate chip instead of opening the attach sheet.
- **`DPAD_LEFT` from inside the composer moves the caret, not the focus**, so there is no arrow-key route to `attach` once the composer holds focus.
- The `ACTION_SEND` route was already ruled out in run 2: `am start --grant-read-uri-permission` from the shell grants nothing, because the grant has to come from a real content provider.

Indexing time and the memory step were therefore not measured, again.

## Driver changes since run 2, and the two instrument bugs they fixed

Run 2 ended early because the driver reached controls by pressing TAB until the focused resource-id matched, which F27 breaks. Run 3's driver was rebuilt around three rules, and all three had to be found the hard way in the first 40 minutes of this session.

1. **Reach the composer by resource-id, with DPAD as the escape.** `focus_composer()` dumps once, and if focus is already on `composer-input` it stops there. Otherwise it presses `DPAD_DOWN` twelve times blind — no dumps, ~0.15 s each — which walks to the bottom bar from any state including the chip trap, then dumps once and steps `DPAD_LEFT` from `mic`/`send` or `DPAD_RIGHT` from `attach`. TAB is kept only as a fallback for the states where the ring is well behaved. The first version of this helper hunted focus with a dump after every key and cost up to 130 s per prompt, which would have produced another thin run; the blind-press version costs 15–20 s.
2. **Do not count assistant rows to detect completion.** `uiautomator dump` returns only the visible window, so an older answer scrolls out and a row count does not grow. Two intermediate versions of `s-send.sh` failed on this: counting rows timed out at 250 s per prompt, and so did reading `assistant-text`, whose `text` attribute is empty (the node is a `ViewGroup`; the answer's first line lives in the **`assistant-message` node's `content-desc`**). The shipping check is: no `stop` node on screen, the last `assistant-message` `content-desc` differs from the one captured before the send, and it is stable across two consecutive dumps.
3. **Waiting only for the stop button is not enough.** Run 2's `s-send.sh` waited for `stop` to appear and then vanish. A three-second answer finishes before the first dump lands, `stop` is never seen, and the wait burns its whole budget — 407 s on one arithmetic prompt here before the check was replaced. `stop-seen=0` with `complete=1` in `events.log` marks the answers that were simply faster than the instrument.

Run 2's other two instrument errors are also closed: the banner grep now uses the shipping string `Paused while Inborn was in the background`, and `analyze.sh` extracts the pid with `grep -oE 'pid=[0-9]+'` instead of a `sed` that captured stray text, so the package-scoped red-marker count is real this time.

## Observations for the owners (not soak failures)

1. **Instant does not terminate on Hebrew.** All three non-completions were the instrument's budget expiring while generation was still running (`stop-seen=1`), and two of them were the **same prompt**: "Answer in Hebrew: what is the meaning of the word shalom?" on Instant, at minute 6 (422 s) and again at minute 73 (417 s). The third was "Continue." at minute 147 (453 s). The catalog that shipped in fixes-r13 now rates Instant **"No · Hebrew"**, and this is the behaviour behind that rating: not merely a weak answer but a generation that runs past seven minutes. Run 1 noted the model's Hebrew was "word salad"; this run shows it also fails to stop. Worth a look from whoever owns the repetition guard, since the guard did not cut these off.
2. **The driver recovered from all three without touching the app.** Each time, focus was left on `open-chats`, the recovery branch pressed BACK and re-fronted the activity, and the next prompt answered normally. No send ever failed for lack of a reachable composer.
3. **PSS tracks the resident model cleanly**, ~0.97–1.14 GB on Instant and ~1.63–1.85 GB on Fast, with the switch visible within one sample each time. Peak 1.85 GB on 8 GB left headroom throughout.
4. **Skin temperature peaked at 40.2 °C**, essentially run 2's 40.0 °C and well below run 1's 43.3 °C, on a heavier prompt load than run 2 carried.
5. **The engine reloads more often than the model switches.** 10 `llama.rn loaded model INSTANT` and 9 `llama.rn loaded model FAST` lines inside the window against only 5 model switches, so a load also happens on other transitions. Not a fault, but it is where the 36 s and 60 s first-token readings in the ledger come from.
6. `dumpsys meminfo` did not time out once, because the app was only ever sampled while foregrounded (run 1's lesson, kept).
