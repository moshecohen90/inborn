## Build
```
cd apps/mobile && rm -rf ios && npx expo prebuild -p ios --no-install --clean && (cd ios && pod install)
cd ios && xcodebuild -workspace Inborn.xcworkspace -scheme Inborn -configuration Release -destination "generic/platform=iOS" \
  -archivePath build/Inborn.xcarchive -derivedDataPath build/dd -allowProvisioningUpdates DEVELOPMENT_TEAM=NGCHN95667 archive
eval "$(../../../scripts/asc-key-env.sh)"
xcodebuild -exportArchive -archivePath build/Inborn.xcarchive -exportOptionsPlist ExportOptions.plist -exportPath build/export \
  -allowProvisioningUpdates -authenticationKeyPath "$INBORN_ASC_KEY_PATH" -authenticationKeyID "$INBORN_ASC_KEY_ID" \
  -authenticationKeyIssuerID "$INBORN_ASC_ISSUER_ID"
xcrun altool --validate-app -f build/export/Inborn.ipa -t ios --apiKey "$INBORN_ASC_KEY_ID" --apiIssuer "$INBORN_ASC_ISSUER_ID"
xcrun altool --upload-app  -f build/export/Inborn.ipa -t ios --apiKey "$INBORN_ASC_KEY_ID" --apiIssuer "$INBORN_ASC_ISSUER_ID"
../../../scripts/asc-key-env.sh --cleanup
```

### F39 tables, read out of Hermes bytecode again

Build 11 recorded why a plain `strings` pass finds none of these: Hermes stores any string containing a non-ASCII
character as **UTF-16LE**, and three of the four tables carry `cómo` / `spät` / the Hebrew and CJK markers. Searching the
raw bytes in both encodings finds each table's exact source from `length.ts`, once, exactly as in build 11:

| table | source length | found as |
|---|---|---|
| `EXPLAIN_STARTS` | 219 chars | UTF-16LE ×1 |
| `EXPLAIN_NOT` | 204 chars | UTF-16LE ×1 |
| `EXPLAIN_MARKS` | 834 chars | UTF-16LE ×1 |
| `CHOICE_MARK` | 23 chars | UTF-8 ×1 (pure ASCII) |

## The export failed once, on a full disk

Worth recording because it will happen again. The first `-exportArchive` ran 14:06:21 → 14:08:57 and ended
`error: exportArchive Zip failed`, `** EXPORT FAILED **` — two lines, no cause named. The cause was the Mac:
`/System/Volumes/Data` had **297 MB** free of 1.8 TB, and the export has to write a ~535 MB zip. Deleting this build's
own `ios/build/dd` (2.7 GB of derived data the finished archive no longer needs) took the volume to 3.0 GB free and the
identical command then succeeded on the first try, 14:09:42 → 14:11:44, `** EXPORT SUCCEEDED **`. Nothing else was
deleted and no other stream's artifacts were touched. The volume later returned to ~97 GB free on its own, from another
stream clearing up.

If `exportArchive Zip failed` ever shows up again, check `df -h /System/Volumes/Data` before anything else. The five
finished iOS worktrees hold about 4.1 GB each in `apps/mobile/ios/build`, and `~/Library/Developer/Xcode/DerivedData`
was 72 GB during this run.

## Cloud signing: the Admin key, now by default

Builds 6–11 each had to pick the Admin key by hand. Since `scripts/asc-key-env.sh` landed on `main` (commit 2a7b8f7,
merged bfe9a0d) the Admin key is the script's default and the export, `--validate-app` and `--upload-app` all read it
from the Keychain with no decision to make. Export succeeded on the first authenticated attempt. The `.p8` is written
to `~/.appstoreconnect/private_keys` with mode 600 for the run and deleted after: verified at the end of this run —
`~/.appstoreconnect/private_keys` holds **0** entries and a `find` for `*.p8` over the worktree and the scratch dir
returns **0** files.

The underlying App Manager fault is unchanged and still open for the lead if `inborn-asc-api` is ever to be usable:
Apple answers `GET /xcbuild/v1/certificates?filter[certificateType]=DISTRIBUTION_MANAGED` for that key with 403
`FORBIDDEN_ERROR`, resultCode 7495. The default now routes around it rather than hitting it.
