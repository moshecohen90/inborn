## 2. The deploy-script bug: `_headers` was an asset, not configuration

`readDist` put `/_headers` in the uploaded manifest. Workers static assets then served it verbatim at
`/_headers` (`200`) and applied none of it: the app origin answered **with no `Cross-Origin-Opener-Policy`, no
`Cross-Origin-Embedder-Policy` and no `Content-Security-Policy`** — which is exactly the isolation pair the WASM
engine needs for `SharedArrayBuffer`, so the first deploy would have shipped an origin quietly stuck on the
single-thread fallback. The file now travels as `assets.config._headers` (what wrangler sends) and is kept out of the
manifest.

`/_redirects` is dropped rather than forwarded: the web build writes the Pages-style `/* /index.html 200`, and
Cloudflare rejects it here — `400 100324 Invalid _redirects configuration: Line 1: Infinite loop detected in this
rule` — because `not_found_handling: single-page-application` already is that rule.

Before and after on `https://app.inbornapp.com/`:

| | before | after |
|---|---|---|
| `Cross-Origin-Opener-Policy` | absent | `same-origin` |
| `Cross-Origin-Embedder-Policy` | absent | `require-corp` |
| `Content-Security-Policy` | absent | the full policy from `apps/web/headers.mjs` |
| `GET /_headers` | `200`, the file itself | `200` SPA shell (site: `404`) |

# Second pass, same day: HSTS, /download, and two review findings that were already fixed

Two reviews landed after the deploy above. Both were re-checked live before anything was changed.

## What the reviews reported, and what the origins actually sent

| Reported | Live at the time of re-check |
|---|---|
| "inbornapp.com sends NO security headers" | CSP, COOP, CORP, Permissions-Policy, Referrer-Policy, X-Content-Type-Options, X-Frame-Options all present |
| "`/_headers` is downloadable at 200 with the CSP inside" | `404` on the site |
| "app.inbornapp.com has NO DNS record, the app half never went live" | `A 104.21.70.137 / 172.67.223.209` from the zone's own nameservers and from Cloudflare's resolver, `200` with COOP + COEP on all four published edge addresses |

Both reviews were reading the state left by the **first** deploy of the evening, which did ship `_headers` as an
asset; the fix in the section above had already landed by the time they were written. The DNS finding is the
negative-cache artefact documented above: the reviewer's resolver, like this Mac's, still held the pre-deploy
`NXDOMAIN`. Nothing was rebuilt on the strength of either report.

## What was genuinely missing, and is now done

**1. HSTS.** Neither `_headers` file asked for `Strict-Transport-Security`, so neither origin sent it. Added to
`apps/site/public/_headers` and to `apps/web/headers.mjs` (the one definition of the web origin's headers), and it
survives the `assets.config._headers` path:

```
$ curl -sD - -o /dev/null https://inbornapp.com/     -> strict-transport-security: max-age=31536000
$ curl -sD - -o /dev/null https://app.inbornapp.com/ -> strict-transport-security: max-age=31536000
```

No `includeSubDomains` and no `preload`. Each origin speaks for itself: `includeSubDomains` would bind every future
host on the zone to HTTPS for a year, including one that does not exist yet, and `preload` is the entry that cannot
be withdrawn on our schedule. Zone-wide HSTS is an SSL/TLS setting and needs Zone → Settings → Edit, which this
token deliberately does not have.

**2. `/download` was a 404 that three live buy buttons pointed at.** `STORE_LINKS` in
`apps/mobile/src/web/links.ts` sends the web paywall's App Store, Google Play and Desktop buttons to
`https://inbornapp.com/download`, and the page did not exist. `apps/site/src/pages/download.html` now does: the two
store tiles from the same `{{STORE_ROW}}` token the home page uses (so they read "Opens at launch" until
`STORES_LIVE=1`, in one place), a working tile for the browser version, an honest "Not yet" tile for Windows and
macOS rather than a link that goes nowhere, the GitHub line, and refunds pointing at `/support`. It is in
`sitemap.xml` and in the `llms.txt` Product group.

```
$ curl -s -o /dev/null -w '%{http_code}' https://inbornapp.com/download   -> 200
```

Rendered at 390, 768, 1024 and 1440: `docs/qa/deploy-site/download-390.png`, `-768`, `-1024`, `-1440`.

## What was asked for and deliberately not built

- **A `main_module` Worker that re-parses `_headers` and applies the rules itself.** Not needed. The platform already
  applies them from `assets.config._headers`, which is proven by every header table above and by the per-path
  `Cache-Control` rules arriving too. Putting a Worker in front of every asset request to re-implement a feature the
  runtime provides would be a second mechanism doing the first one's job.
- **`/_headers` returning 404 on the app origin.** It returns the SPA shell, not the file, because
  `not_found_handling: single-page-application` answers every unknown path with `index.html`. That is the setting
  that makes `/paywall` and every other deep link work; turning it off to make one path 404 would break them. The
  file itself is not in the manifest, so nothing is disclosed. On the site, where `not_found_handling` is
  `404-page`, `/_headers` and `/_redirects` both return `404`.

## Cross-origin isolation, end to end

`pn web:smoke` against the same build reports `isolated=true` on the first visit (ready 17.3 s, 32.3 tok/s, threads=6)
and 0 model fetches on the offline visit. That is the COOP/COEP pair being honoured by a real browser, not just two
header lines in a `curl` dump, which is what the `_headers` bug would have silently cost.

# Round 57 — analytics injection (F275)

Cloudflare was adding its own Web Analytics beacon to every HTML response on both origins. Nothing we upload
contained it, and no build gate could have caught it, because the injection happens at the edge on the way out.

## Before

```
$ curl -s -H 'User-Agent: Mozilla/5.0 (Macintosh) Chrome/140.0' -H 'Accept: text/html' \
    https://inbornapp.com/ | grep cloudflareinsights
<script type="module" src="https://static.cloudflareinsights.com/beacon.min.js/v31edd6df95cf4e85bb4c19e7a9bdbcba1788362987495"
  integrity="sha512-iIg7k2xntmwu6/uSb5tpc/hySgZc4eoL31yB29W6tJFo2akwjPWcEqnCEdJvGexCL0KEQwVYv5BlowfhVz26hg=="
  data-cf-beacon='{"version":"2024.11.0","token":"8316c4ee7938495c83ccf9867432a34c","r":1,"spa":2}' crossorigin="anonymous">
```

The same tag, the same token, on `https://app.inbornapp.com/`.

**The trigger is `Accept: text/html`, not the user agent.** With the browser UA alone the response is clean; with
`Accept: text/html` alone the beacon is there. That is why a plain `curl`, and every check we run against `dist`,
saw nothing.

It matters beyond tidiness. Both CSPs forbid off-origin scripts, so a real browser refused to load it and logged an
error on every page view; the site footer claims no third-party requests; and the app's own Proof screen claims
`TRACKERS 0`.

## There was no setting to turn off

Checked from the dashboard session before changing anything:

| Check | Result |
|---|---|
| `GET /accounts/{acc}/rum/site_info/list?per_page=200` | 200, **11 sites**, none for `inbornapp.com`, none carrying token `8316c4ee…` |
| Same list, token search | `hasToken: false`, `hasInborn: false` |
| `GET /zones/{inbornapp.com}/rulesets` | three managed rulesets only (normalization, managed WAF, DDoS L7); **no RUM ruleset** |
| `GET /accounts` | one account; there is no second one holding the site |
| `GET /accounts/{acc}/workers/scripts/inborn-site/script-settings` | `observability: null` |
| `GET /accounts/{acc}/rum/site_info/list` with the Keychain deploy token | `403` — that token has no Web Analytics permission by design |

For comparison, `hebrewbible.app` gets token `485f89c5…`, which **is** its own Web Analytics site in that list with
`auto_install: true`. So auto-install behaves normally where a site exists. On `inbornapp.com` the beacon arrives
with no site, no ruleset and no toggle behind it: it is the Workers platform injecting its own, which is the
long-standing Pages behaviour reported as "injected despite Web Analytics being disabled, no UI toggle".

## The fix, in the repo

`Cache-Control: no-transform` tells Cloudflare not to rewrite the response. It is now part of the single definition
of each origin's headers, so it cannot drift:

- `apps/site/public/_headers` — on `/*`, `/fonts/*` and `/site.css`.
- `apps/web/headers.mjs` — a `cache()` helper appends it to every `Cache-Control` the generator writes, and `/*`
  now carries `public, max-age=0, must-revalidate, no-transform`, which is the value the platform was already
  sending for the shell. No freshness changed; only the directive was added.

**Proven as a controlled experiment, not asserted.** The site was deployed with `no-transform` first, alone:

```
site  (no-transform)   beacon matches: 0, 0, 0   cache-control: public, max-age=600, no-transform
app   (unchanged)      beacon matches: 1
```

Then the app was deployed and both went to zero. The app's `<script src>` count fell from 2 to 1, the one remaining
being its own Expo bundle.

## The gate that would have caught it

`scripts/check-live.mjs` (`pn check:live`) asks the **public URL** with a browser's `Accept: text/html` and fails on

- any occurrence of `cloudflareinsights`,
- any `<script src>` whose resolved origin is not the page's own,
- a response whose `Cache-Control` has no `no-transform`.

`scripts/deploy-cloudflare.mjs` runs it on the origins it just deployed, eight seconds after the last upload, and
exits non-zero if it fails; `--no-check-live` skips it.
