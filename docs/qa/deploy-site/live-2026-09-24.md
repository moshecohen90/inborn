# inbornapp.com and app.inbornapp.com are live — 24.9.2026

Both origins serve. The block recorded in `curl-evidence.md` was one missing API-token permission, and behind it one
bug in the deploy script: the `_headers` file was uploaded as an ordinary asset, so the edge served it and applied
nothing. Both are fixed; every line below is a real response from the public internet.

Account `9de3aac0325f2ec6294e00714a0772b7`, zone `inbornapp.com` = `ef6602f264e66593cd9d21a18809258a`.
Deployed with `node scripts/deploy-cloudflare.mjs --site --app`.

First proof it is not read-only, the exact call that used to answer `403`:


**Cloudflare's dashboard cannot create this token.** In the current dashboard, Zone Resources → **"Specific zone" is
rendered disabled** (`aria-disabled="true"`) on the Create Custom Token form, whatever the account resource or the
permission rows are, so a zone-scoped token cannot be built by clicking. The token was created by the dashboard's own
`POST /api/v4/user/tokens` call with the zone resource set to `com.cloudflare.api.account.zone.ef66…258a`; the same
call made from outside the page is refused by the WAF with a `403` challenge page, so it has to originate in the
dashboard. If this token ever has to be rebuilt, expect that, and check the option's state before assuming a
mis-click.

## 2. The deploy-script bug: `_headers` was an asset, not configuration

`readDist` put `/_headers` in the uploaded manifest. Workers static assets then served it verbatim at
`/_headers` (`200`) and applied none of it: the app origin answered **with no `Cross-Origin-Opener-Policy`, no
`Cross-Origin-Embedder-Policy` and no `Content-Security-Policy`** — which is exactly the isolation pair the WASM
engine needs for `SharedArrayBuffer`, so the first deploy would have shipped an origin quietly stuck on the
single-thread fallback. The file now travels as `assets.config._headers` (what wrangler sends) and is kept out of the
manifest.

`/_redirects` is dropped rather than forwarded: the web build writes the Pages-style `/* /index.html 200`, and
Cloudflare rejects it here — `400 100324 Invalid _redirects configuration: Line 1: Infinite loop detected in this
rule` — because `not_found_handling: single-page-application` already is that rule.

Before and after on `https://app.inbornapp.com/`:

| | before | after |
|---|---|---|
| `Cross-Origin-Opener-Policy` | absent | `same-origin` |
| `Cross-Origin-Embedder-Policy` | absent | `require-corp` |
| `Content-Security-Policy` | absent | the full policy from `apps/web/headers.mjs` |
| `GET /_headers` | `200`, the file itself | `200` SPA shell (site: `404`) |

## 6. DNS

Attaching each hostname to its Worker wrote the proxied record; nothing was written by hand.

| name | A records | Worker |
|---|---|---|
| `inbornapp.com` | `104.21.70.137`, `172.67.223.209` | `inborn-site` |
| `www.inbornapp.com` | same | `inborn-www-redirect` |
| `app.inbornapp.com` | same | `inborn-app` |
| `models.inbornapp.com` | same | R2 catalogue (untouched) |

`GET /accounts/{acc}/workers/domains` lists exactly those three, all `production`.

**One caching artefact, not a fault.** `app.inbornapp.com` was `NXDOMAIN` for months, so resolvers asked before the
deploy hold a negative answer until the zone's 1800 s SOA minimum expires. Cloudflare's resolver and the zone's own
nameservers returned the new records immediately; Google Public DNS, which is this Mac's first resolver, answered
`NXDOMAIN` for about half an hour and then returned `188.114.97.7` / `188.114.96.7`. Both of those edge addresses
serve `200` on the apex and on the app, so the hostname is public. The checks above were made with
`curl --resolve` while the local resolver was still holding the stale answer; nothing about either origin depends on
it, and macOS clears its own copy without help.
